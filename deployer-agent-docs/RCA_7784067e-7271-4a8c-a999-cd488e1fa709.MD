# RCA — "Datenschutzerklärung"-Link öffnet nicht in der nativen iOS-App

Deployment: leonida-preview-2 (f023b72d…) · Active run: 7784067e-7271-4a8c-a999-cd488e1fa709 (redeploy, success)
Live-URL: https://leonida-preview-2.emergent.host · Template: farm_ts_react_mongo_base_image · frontend_type: kubernetes (nginx, statische Dateien) · Tier: tier_0

## Problemstellung
In der nativen Capacitor-iOS-App lässt sich der Link „Datenschutzerklärung" (Profil/Einstellungen) nicht öffnen. Ziel: Route `/datenschutz`, öffentlich ohne Login, gültige HTTPS-Adresse, funktionierendes Zurück, am iPhone lesbar/scrollbar. Untersuchen: Produktion, iOS-/Capacitor-Routing, Server-Routing, Deployed-Asset/Rewrite-Verhalten, aktuelle Produktionsversion.

## Was geprüft wurde (Evidenz)
Quelle = gepullter Source des aktiven (deployten) Runs, extrahiert im Eph-Pod.

1. **Route ist öffentlich — kein Auth-Gate.** `src/routes/datenschutz.tsx` nutzt `createFileRoute("/datenschutz")` mit `component: Privacy`, **kein** `beforeLoad`/Auth-Guard. Kein Redirect auf /login im Code.
2. **Route ist gebaut und verdrahtet.** Im deployten Bundle (`assets/index-*.js`, `routes-*.js`) ist die Route registriert: `('/datenschutz')({head:()=>({meta:[{title:'Datenschutz · Leonida Explorer'}…]}), component: …import('./datenschutz-CkL3scik.js')})`. Der Lazy-Chunk `datenschutz-CkL3scik.js` existiert. `src/routes/profil.tsx` rendert den Link als `<Link to="/datenschutz" data-testid="profile-privacy-settings-link">` (Client-seitige TanStack-Navigation) und ist **nicht** hinter `isNativeApp()` versteckt.
3. **Server liefert /datenschutz aus (200).** `preview_health_check` auf `/datenschutz` und `/datenschutz/` → HTTP 200, HTML-Shell. Kein 404, kein 5xx, kein Redirect auf eine Login-URL.
4. **Capacitor server.url ist korrekt.** `capacitor.config.ts` **und** die synchronisierte native Config `ios/App/App/capacitor.config.json` setzen `server.url = "https://leonida-preview-2.emergent.host"` (gültige HTTPS-Prod-URL, `cleartext:false`, `limitsNavigationsToAppBoundDomains:false`). **Kein** localhost, **keine** interne Preview-Domain.
5. **Zurück-Button vorhanden.** `src/components/LegalPage.tsx`: `onClick={() => (window.history.length > 1 ? router.history.back() : router.navigate({ to: "/" }))}` — funktionierendes Zurück, Fallback auf `/`.
6. **iPhone-Layout ok.** `AppShell` nutzt `min-h-dvh`, `env(safe-area-inset-*)`, scrollbaren `<main>`. LegalPage ist scrollbarer Text.
7. **SPA/CSR-Rendering (wichtig).** Das Frontend ist TanStack Start im SPA/Prerender-Modus; alle Route-Shells sind identische, leere CSR-Shells. Deshalb liefert der Server für **jede** Route denselben Shell mit dem Default-Titel „Anmelden · Leonida Explorer" aus — auch `/datenschutz/`. Der korrekte Titel „Datenschutz" wird nach dem Boot **client-seitig** über das route-eigene `head()` gesetzt. Das ist rein kosmetisch (Titel/SEO beim Hard-Load) und **blockiert das clientseitige Rendering nicht**.
8. **nginx (`nginx.conf`, via Dockerfile nach `/etc/nginx/nginx.conf` kopiert):** `location / { try_files $uri /index.html; }` — es fehlt `$uri/`. Für `/datenschutz` (Verzeichnis ohne Trailing-Slash) fällt try_files auf `/index.html` zurück. Da aber **alle** Route-Shells identisch sind, hat das hier **keinen** beobachtbaren funktionalen Effekt (sowohl `/datenschutz` als auch `/datenschutz/` liefern 200 denselben Shell).

## Root Cause
In der **aktuellen Produktionsversion (Web/PWA) ist die Route korrekt**: `/datenschutz` ist öffentlich, gebaut, verdrahtet, liefert 200 und wird clientseitig gerendert; der Deep-Link ist ein normaler Client-`<Link>`; `server.url` zeigt auf die korrekte Live-HTTPS-Domain (in TS- und nativer Config). Ein **server-, routing-, asset-/rewrite- oder config-seitiger Defekt, der den Link blockieren würde, ist nicht reproduzierbar.**

Der Fehler tritt ausschließlich in der **installierten nativen App** auf. Die iOS-App wird **außerhalb** dieser Web-Deploy-Pipeline gebaut und verteilt (siehe `codemagic.yaml` → Workflow `ios-testflight` → TestFlight/App Store). Ein Web-Redeploy aktualisiert das auf dem iPhone installierte Binary **nicht**. Wahrscheinlichste Ursache: das installierte Binary ist ein **älterer Codemagic/TestFlight-Build**, der vor der Finalisierung von Route/`server.url` erstellt wurde (bzw. noch auf eine alte/Preview-URL zeigte, wie der Hinweis „server.url historically…" nahelegt), oder ein geräteseitiger WebView-/SW-Cache. Das Route-Rendering kommt zwar vom Server, aber die eingebackene `server.url` stammt aus dem Binary. (Diese geräteseitige Ursache ist inferenziell — das installierte Binary selbst ist mit den vorhandenen Tools nicht einsehbar.)

## Betroffene Dateien/Config
- Korrekt / kein Fix nötig: `src/routes/datenschutz.tsx`, `src/routes/profil.tsx`, `src/components/LegalPage.tsx`, `capacitor.config.ts`, `ios/App/App/capacitor.config.json`.
- Verteilung der iOS-App: `codemagic.yaml` (ios-testflight) — out-of-band, nicht Teil dieses Web-Deploys.
- Optional/kosmetisch: `nginx.conf` `try_files $uri /index.html;` → `try_files $uri $uri/ /index.html;` (korrekter Deep-Link-Titel/SEO). **Nicht** die funktionale Ursache.

## Ist ein Redeploy nötig?
- **Web/PWA:** Nein. Die Produktion liefert `/datenschutz` bereits korrekt aus. In Safari unter https://leonida-preview-2.emergent.host/datenschutz lädt die öffentliche Datenschutzseite.
- **Native iPhone-App:** Ein Web-Redeploy hilft **nicht**. Erforderlich ist ein **neuer Codemagic-iOS-Build** (Workflow `ios-testflight`) mit anschließender TestFlight/App-Store-Verteilung; danach die App auf dem iPhone aktualisieren. Dabei verifizieren, dass im Build `server.url=https://leonida-preview-2.emergent.host` steckt.
- Falls der optionale nginx-Feinschliff gewünscht ist, wäre dafür ein Web-Redeploy nötig (aber niedrige Priorität, nicht die Ursache).
