# RCA — Leonida Explorer: „The spot could not be unlocked." (Fundort-Freischaltung)

## Problem statement
On a locked Fundort (spot) the iPhone app shows the unlock panel ("first ten spots free", balance 16 coins), but tapping unlock returns **"The spot could not be unlocked."**. Reported in BOTH Preview and Production. Diagnose against prod `https://leonida-preview-2.emergent.host` without changing data.

## Architecture of the unlock flow (important)
This is a Lovable-origin app. The **unlock does NOT go through the Emergent FastAPI / MongoDB backend at all.** It is a direct browser → Supabase RPC:
- `src/routes/fundort.$id.tsx` → `useUnlockSpot()` in `src/lib/arcade.ts` → `sb.rpc("unlock_spot", { _spot: spotId })`.
- `sb` = Supabase client (`src/lib/db.ts` → `@/integrations/supabase/client`) pointing at project **`daxzwbkacxllrejaghym.supabase.co`** (`VITE_SUPABASE_URL` / `VITE_SUPABASE_PUBLISHABLE_KEY` in `.env`).

Consequences for diagnosis:
- The Emergent prod pod's MONGO_URL / REACT_APP_BACKEND_URL / nginx /api routing / FastAPI play **no role** in unlock. Confirmed by backend logs: over 24h the backend only served `/api/payments/*` and `/api/push/*` — **zero** unlock requests ever reach it.
- The Supabase binding itself is **healthy in production**: `my_spot_access` RPC returns `false` (that is exactly why the locked panel and "first ten free" text render), and the coin balance (16) is read via `my_coin_balance` RPC. If the Supabase URL/key were wrong or unauthenticated, those sibling RPCs would also fail. So this is NOT a secret / env / routing / connection-binding problem.

## Root cause (confirmed by code + migration evidence)
The error string is the i18n key `"Die Fundort-Freischaltung konnte nicht abgeschlossen werden."` → "The spot could not be unlocked." This is the **generic fallback** of `spotUnlockError()` in `src/lib/arcade.ts`. That fallback is reached ONLY when the RPC error is:
- NOT a missing-object code (`isMissing` = PGRST205/PGRST202/42703/42P01/42883/PGRST200) → so the function **does exist** (migration 013 is installed; `my_spot_access` + `spot_unlocks` table also prove 013 ran), AND
- NOT `AUTH_REQUIRED`, `INSUFFICIENT_COINS`, `SPOT_NOT_FOUND`, AND
- NOT SQLSTATE `23505` (already unlocked) or `42501` (RLS/permission).

The production Supabase database is still running the **013** version of `public.unlock_spot`, which contains an **ambiguous column reference**:
```sql
-- 013_arcade_coins_spot_unlock.sql (the version live in prod)
select balance into b from public.coin_wallets where user_id = uid for update;
```
`balance` is both the `coin_wallets.balance` column AND the function's OUT column `balance integer` in `returns table(unlocked boolean, cost integer, balance integer, ...)`. With no `#variable_conflict` directive and no table qualification, PostgreSQL raises **SQLSTATE `42702` — "column reference \"balance\" is ambiguous"**. `42702` is not handled by any branch of `spotUnlockError()`, so the UI shows the generic "The spot could not be unlocked."

This is independently corroborated by the fix migration already present in the source tree, **`docs/migrations/015_spot_unlock_fix.sql`**, whose header states verbatim:
> "Korrektur: Spalten sind jetzt eindeutig benannt (vorher Fehler 'column reference balance is ambiguous')."

`015` rewrites `unlock_spot` with `#variable_conflict use_column` and fully table-qualified columns (`w.balance`, `su.user_id`, …). **`015` has not been executed in the production Supabase project**, so prod still fails on the 013 ambiguity.

This explains every observed fact:
- Fails in BOTH Preview and Production — both frontends talk to the **same** Supabase project (`daxzwbkacxllrejaghym`); the broken function is shared.
- The error is the generic message (unmapped `42702`), not the "run SQL 013 in Lovable" message (which would require a *missing* function) and not INSUFFICIENT_COINS.
- Balance 16 / first-ten-free is irrelevant: on the free path (`charge = 0`) the function still executes the ambiguous `select balance into b` and errors before completing.

## What this is NOT
- Not a frontend bug — `src/lib/arcade.ts` / `fundort.$id.tsx` already call the RPC correctly and the source already contains the corrected 015 SQL.
- Not an Emergent backend / Mongo / FastAPI / nginx-routing issue (unlock never touches them).
- Not a secret / env-binding issue (sibling Supabase RPCs succeed in prod).
- Not INSUFFICIENT_COINS and not a tier/resource issue.

## Verification performed
- `describe_deployment_state`, `preview_health_check` → app live/healthy (200).
- `fetch_app_logs` (24h) → no unlock traffic to the Emergent backend; only `/api/payments/*`, `/api/push/*`.
- Source read in eph sandbox: `src/routes/fundort.$id.tsx`, `src/lib/arcade.ts`, `src/lib/db.ts`, `.env`, and SQL `docs/migrations/013_arcade_coins_spot_unlock.sql` + `015_spot_unlock_fix.sql`.
- NOT verified by live execution: I cannot run SQL against the user's Supabase project (no tool/credentials; `mongo_query` is Mongo-only and this app's data is in Supabase). The 42702 attribution is inferred from the code paths and the 015 migration's own documentation of this exact prior error, not reproduced live.

## Fix
**User action in Supabase (Lovable):** Open the Lovable / Supabase SQL editor for project `daxzwbkacxllrejaghym` and execute **`docs/migrations/015_spot_unlock_fix.sql`** (it is `create or replace function` and additive — safe, no data change). This replaces the ambiguous 013 `unlock_spot` with the column-qualified version. After it runs, unlocking the first ten spots (cost 0) and paid unlocks (150 coins) will succeed. No redeploy of the Emergent app is required; no production data migration is needed.

Optional hardening (E1 / source, not required for the fix): add a `42702` branch (and a generic Postgres-error catch) to `spotUnlockError()` so any future unmapped DB error surfaces a clearer message instead of the blanket fallback — but this is cosmetic; the real fix is running migration 015.
