# Leonida Explorer – Spec (kurz)
TanStack Start + Lovable Cloud (Supabase). Mobile-first GTA-VI-Community-Karte.
- Auth: Supabase E-Mail/Passwort, E-Mail-Bestätigung an. Store: `src/lib/store.tsx` (useStore: user, authReady, signIn, signUp, signOut).
- Passwort vergessen: Login-Modus "forgot" -> resetPasswordForEmail(redirectTo origin+/passwort-neu); Seite `src/routes/passwort-neu.tsx` setzt updateUser({password}). Store-Flag `recovery` leitet Recovery-Sitzungen von / nach /passwort-neu.
- Rollen: `user_roles` (user/admin). Admin-Flag = `supabase.rpc("has_role")` mit Nutzer-Token (DB-seitig); alle Admin-Schreibzugriffe per RLS gesichert. Admins nur via Lovable/SQL eintragen.
- Profile: `profiles` (username, avatar_url, bio, xp). Level-Mathe nur `src/lib/levels.ts`.
- Fundorte: Tabelle `spots` via useStore (Query ["spots", uid]); RLS: Gäste approved, Autor eigene, Admin alle. addSpot -> insert pending + Upload nach `spot-photos/<uid>/<spotId>/…` + `spot_photos`. setStatus -> update (nur Admin, RLS). XP nur per DB-Trigger (003: 50 XP, dedupe über xp_events unique).
- Likes/Merken: noch nur localStorage. Keine Demo-Daten mehr.
- DB-Änderungen nur als Entwurf in `docs/migrations/` (002_auth_roles.sql), angewendet über Lovable.
- Emergent-Deployment (FARM-Template: statisches SPA via nginx + FastAPI): `frontend/` ist nur ein Wrapper (dev: `cd .. && yarn dev`; build: `node build.mjs` -> EMERGENT_SPA=1 vite build -> `.output/public` nach `frontend/dist` + `frontend/build`, index.html = _shell.html, je Route eigene index.html). `backend/server.py` = Minimal-FastAPI mit `/api/health`, keine DB. Lovable-Build/SSR unverändert.
- Karte: `src/routes/karte.tsx` (Layout nach Designvorlage), `MapCanvas` (Bild `src/assets/leonida-map.jpg` 827×1140, Fundorte x/y in %): misst die Fläche (ResizeObserver) und passt die Karte per "contain" ein (Scale 1 = ganze Karte, bis 8×), Pins gegenskaliert (--pin-scale). `variant` "card" (Beitrag-Auswahl) / "floating" (Kartenseite, füllt Resthöhe). Das Bild blendet jetzt nur seine äußeren Wasserbereiche an allen vier Seiten per Safari-kompatibler CSS-Maske aus; Marker und Touch-Fläche bleiben unmaskiert. Glocke: Admin -> /admin (Punkt bei pending), Spieler -> /profil (eigene pending). AppShell-Prop `vividBg` nur für Karte.
- Profile/Abzeichen (SQL 004 + 004b, Entwurf in docs/migrations; Selbsttest 006; XP-Korrektur 005 optional): Store liest Profile über View `profile_cards` (Privatsphäre maskiert), Rückfall auf `profiles` wenn View fehlt (`isMissing` in src/lib/db.ts). Profilbilder: privater Bucket `avatars` (<uid>/<uuid>.jpg, 512px JPEG, signierte URLs), Zuschnitt `src/components/AvatarEditor.tsx` (react-easy-crop). Abzeichen: Katalog `src/lib/badges.ts` = Tabelle `badges`; Bilder `public/badges/<id>.webp`; Vergabe nur per DB-Funktionen (check_badges, Spenden-Trigger). `src/lib/social.ts`: Abzeichen, Fortschritt (`my_badge_progress`), Monatswertung (`monthly_leaderboard`), Korrekturen, Genauigkeit (`set_spot_accuracy`), Spenden, Avatar-Upload. Likes in `spot_likes`; aktive Tage via `touch_activity()` beim App-Start. SQL 004 legt die Profil-Privatsphäre-Spalten vor der Funktion `can_view_avatar()` an, damit ein Erstlauf nicht an `p.is_private` scheitert. 004b sperrt `profiles` auf (id, username) und ersetzt die `user_badges`-Leseregel durch die Security-Definer-Funktion `badges_visible()` (sonst „permission denied“).
- PWA/Updates: `public/manifest.webmanifest` und `public/sw.js` aktivieren Home-Screen-Modus. `src/lib/PwaUpdatePrompt.tsx` registriert den Service Worker mit `updateViaCache: "none"` und einer buildzeitbasierten URL; bei einer neuen veröffentlichten Version erscheint ein bestätigter Update-Hinweis. Der Service Worker lädt same-origin GETs netzwerkpriorisiert mit `cache: "no-store"`, löscht keine localStorage-/Auth-Daten und lädt erst nach Nutzerbestätigung neu.
- Community-Chat (`src/components/chat/GlobalChatRoom.tsx`, Route `/community/chat`, SQL 007): Layout ist ein `fixed` Flex-Container mit Höhe/Top aus `visualViewport` (`--chat-vh`, `--chat-top`) und `padding-bottom = gemessene Höhe der Navigationsleiste (data-testid app-bottom-nav, per ResizeObserver) + 8px`; bei offener Tastatur (innerHeight − visualViewport.height > 120) entfällt die Navihöhe, das Eingabefeld sitzt 8px über der Tastatur. Nachrichtenliste = `flex-1 min-h-0 overflow-y-auto`.
- iPhone: Viewport `maximum-scale=1` verhindert Auto-Zoom bei Eingabefeldern <16px (sonst schwebt die fixierte Navi mitten im Bild); html/body `overflow-x: clip`; `safe-bottom` Utility in styles.css (Home-Balken-Abstand der Navi).

## Benutzernamen-System (SQL 012 – ENTWURF, vom Nutzer manuell in Lovable auszuführen)

- Datenbankmigration: `docs/migrations/012_username_system.sql`. `profiles.username` darf für Alt-Konten NULL sein; neue UI verlangt einen Namen. Bestehende Auth-IDs, Beiträge, Freunde, Chats, XP und Abzeichen bleiben erhalten. Bestehende case-insensitive Konflikte stoppen die Migration bewusst statt Namen still zu verändern.
- Neue Auth-Triggerfunktion `handle_new_user` übernimmt gültige Metadaten; ältere Clients ohne gültige Metadaten erhalten NULL und können später ergänzt werden. Der bestehende auth.users-Trigger wird nicht dupliziert.
- Store: `AppUser.needsUsername`, `updateUsername` via `set_my_username`, invaldiert profiles/spots/social/admin query keys. Profilnamen bleiben Auth-UUID-basierend. `UsernameReminder` ist nicht blockierend und verlinkt Alt-Konten zu Profil → Benutzername.
- Profil: `src/routes/profil.tsx` enthält neon-styled Bereich mit aktuellem Namen, Live-Prüfung und Speichern. `src/components/UsernameField.tsx`, `src/lib/username.ts`, `src/components/UsernameReminder.tsx`.
- Nach Änderung werden Profil-, Fundort- und Social-Abfragen invalidiert; öffentliche Profilroute vergleicht Namen case-insensitive. Namen werden aus den aktuellen Supabase-Profilen in Profil, Freunden, Chats, Fundorten, Benachrichtigungen und Admin-Oberflächen verwendet.

## iPhone-App: „This page didn't load“ nach neuer Veröffentlichung (behoben)
- Ursache: Die iPhone-App lädt die Live-Website (capacitor `server.url`) ohne Service Worker. Die iOS-WebView hält Startseite + altes Haupt-Skript im Zwischenspeicher (HTML ohne Cache-Control, Assets max-age 4 h). Nach einer neuen Veröffentlichung existieren die alten Seiten-Dateien (`/assets/<seite>-ALT.js`) nicht mehr; der Host liefert dafür die HTML-Ersatzseite (200, text/html) -> Modul-Import scheitert -> Root-`errorComponent`. Start ging (schon geladen), Unterseiten nicht. Im Browser/PWA verhindert der Service Worker (network-first, no-store) das.
- Lösung `src/lib/chunk-recovery.ts` (in `__root.tsx` eingebunden): `vite:preloadError` + Fehlerseite erkennen Lade-Fehler alter Dateien und laden die Seite einmalig frisch mit `?_fresh=<zeit>` (umgeht Cache; Schutz: max. 1×/Minute; Parameter wird beim Start sofort entfernt). Nur iPhone-App: beim Start Versionsvergleich (Haupt-Skript `/assets/index-*.js` vs. frisch geladenes `/`) -> sofort frisch laden; beim Zurückkehren in die App -> beim nächsten Seitenwechsel frisch laden (keine Eingaben verloren). Kein neuer TestFlight-Build nötig: wirkt nach dem nächsten Veröffentlichen der Website (einmal App komplett schließen/neu öffnen).
