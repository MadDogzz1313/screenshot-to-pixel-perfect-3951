# RCA — "Leonida Coins bleiben bei 308 stehen" (leonida-preview-2)

## Problemstellung
Nutzer meldet (Preview + Production): Coin-Guthaben scheint bei **308 Leonida Coins** zu stoppen / wächst nicht weiter. Diagnose ausdrücklich read-only, keine Mutationen, keine Coin-Buchungen.

## Wichtige Einschränkung der Untersuchung
Die Coin-Logik dieser App liegt vollständig in **Supabase** (SQL-Funktionen/RPC), nicht in der von der Plattform bereitgestellten MongoDB. Für Supabase existiert **kein Abfrage-Tool** (das `mongo_query`-Tool trifft nur die Plattform-Mongo, die hier keine Coins speichert). Die folgende RCA basiert daher auf **Quellcode-/Migrations-Analyse** des deployten Runs (`4460f959…`), nicht auf einer Live-Abfrage der gebundenen Supabase-DB. Die konkreten Nutzerwerte (aktuelles Wallet, heutige Tagescoins) konnten nicht direkt verifiziert werden — sie sind hergeleitet.

## Befund (belegt aus dem Quellcode)
Coin-Quellen/-Senken im gesamten Repo:
- **Einzige Coin-Quelle:** `finish_arcade_round(...)` (Supabase RPC, aktuell `docs/migrations/016_arcade_rundenwertung_fix.sql`, zuvor 013).
- **Einzige Coin-Senke:** `unlock_spot(...)` (−150 pro Fundort ab dem 11., erste 10 gratis; `docs/migrations/018_spot_unlock_hardening.sql`).
- Guthaben steht in `public.coin_wallets.balance`. Anzeige im Frontend über RPC `my_coin_balance` → `CoinBalance.tsx`. Kein Backend-Python-Pfad berührt Coins.

Entscheidende Zeilen in `finish_arcade_round` (016):
```
select coalesce(sum(cl.delta),0) into day_coins
  from public.coin_ledger cl
  where cl.user_id = uid and cl.reason = 'arcade_round'
    and cl.created_at >= date_trunc('day', now());
...
coin_cap := coins > greatest(0, 300 - day_coins);
coins    := least(coins, greatest(0, 300 - day_coins));   -- TÄGLICHES COIN-LIMIT = 300
...
reward_xp := least(reward_xp, greatest(0, 600 - day_xp)); -- tägliches XP-Limit = 600
```
Rückgabefeld `daily_limit_reached` (`coin_cap or xp_cap`) wird gesetzt und ist im Frontend-Typ `ArcadeRoundResult` vorhanden.

Was im gesamten Code **NICHT** existiert (ausgeschlossene Ursachen):
- **Kein Gesamt-/Wallet-Obergrenze-Cap.** `coin_wallets.balance integer not null check (balance >= 0)` — nur Untergrenze 0, Obergrenze = int4 (~2,1 Mrd.).
- **Keine Konstante `308`** irgendwo in `src/`, `backend/` oder `docs/migrations/` (geprüft).
- **Kein Trigger** auf `coin_wallets` (before/after update) — nichts begrenzt den Saldo.
- **Kein Frontend-Cap.** `CoinBalance.tsx` zeigt `balance.data ?? 0` ungekürzt; `useCoinBalance` gibt `Number(data ?? 0)` zurück.
- **Keine RLS-/Spalten-Begrenzung** auf einen Höchstsaldo.

## Root Cause (hergeleitet)
Es gibt **keine 308-Obergrenze**. Die einzige Mechanik, die Coin-**Zuwachs** stoppt, ist das **tägliche Arcade-Limit von 300 Coins** (`300 - day_coins`, zurückgesetzt um **UTC-Mitternacht** via `date_trunc('day', now())`). Das beobachtete "Stehenbleiben bei 308" ist konsistent mit: vorheriger Restsaldo (z. B. 8) **+ 300 heute erspielte Coins = 308**; danach liefert jede weitere Runde heute `least(coins, 300 - 300) = 0`, der Saldo bleibt bis zum nächsten UTC-Tag unverändert. 308 ist also ein Nutzer-spezifischer Momentwert, kein Limit.

## Sind bestehende Guthaben intakt?
**Ja.** Das Tageslimit kürzt nur Neugutschriften, es reduziert niemals den Saldo. Abbuchungen laufen ausschließlich atomar/idempotent über `unlock_spot` (`FOR UPDATE`-Lock, `coin_ledger`-Unique-Constraints gegen Doppelbuchung, Rollback bei Fehlern). Es wurde keine destruktive oder saldokappende Logik gefunden.

## Empfohlene nächste Schritte
1. **Nutzer/Verifikation:** Am nächsten UTC-Tag prüfen, ob der Saldo durch Arcade-Spielen über 308 steigt. Wenn ja → bestätigt die Tageslimit-Mechanik, kein Defekt. (Idealerweise zur direkten Bestätigung in der Supabase-Konsole read-only prüfen: `select sum(delta) from coin_ledger where user_id=<uid> and reason='arcade_round' and created_at >= date_trunc('day', now());` sollte 300 sein; `select balance from coin_wallets where user_id=<uid>;` = aktuelles Guthaben.)
2. **Produktentscheidung/Code (nur falls höheres Einkommen gewünscht):** Falls das 300/Tag-Limit zu niedrig ist, ist der Wert `300` (und `600` XP) in `finish_arcade_round` (`docs/migrations/016_...sql`) anzupassen. Das ist eine Supabase-SQL-Migration, die **manuell in Lovable/Supabase** ausgeführt werden muss (die Dateien sind als "ENTWURF: manuell ausführen" markiert) — ein reines App-Redeploy ändert die DB-Funktion nicht.

Hinweis: Da keine Live-Supabase-Abfrage möglich war, ist die exakte Zusammensetzung von 308 nicht serverseitig verifiziert; die Mechanik (Tageslimit 300, kein Gesamt-Cap) ist jedoch eindeutig aus dem Code belegt.
