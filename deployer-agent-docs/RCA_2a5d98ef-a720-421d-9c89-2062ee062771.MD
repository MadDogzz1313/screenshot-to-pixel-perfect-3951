# RCA — Leonida Explorer iOS/TestFlight "This page didn't load" (Production)

Deployment: `leonida-preview-2` · Prod URL: https://leonida-preview-2.emergent.host
Active run: `2a5d98ef-a720-421d-9c89-2062ee062771` (redeploy, success) · template: farm_ts_react_mongo_base_image · frontend_type: kubernetes

## TL;DR
The deployment, routing, remote-URL binding, Supabase binding, secrets and production health are **all correct and healthy**. The TestFlight error screen ("This page didn't load / Something went wrong on our end. You can try refreshing or head back home.") is **the app's own client-side React error boundary** (TanStack Router `errorComponent` in `src/routes/__root.tsx`, mirrored by `src/lib/error-page.ts`) firing because route code **throws at runtime inside the iOS WKWebView**.

The reason it works in "web preview" but not in production/TestFlight is architectural: **preview runs the full TanStack Start SSR dev server, while production is built and served as a STATIC CLIENT-ONLY SPA.** SSR pre-renders route HTML in preview and masks any client-runtime fragility; the production SPA executes everything in the browser/WebView, so the same fault only surfaces there — and the iOS app is the only client pointed at production.

## What was verified GOOD (rules out the reported suspects)
1. **Production is reachable and healthy.** `GET /`, `/map`, `/discoveries`, `/community` all return HTTP 200 with the app shell (static `_shell.html`). Backend (FastAPI) logs are clean — only `GET /health 404` (expected; nginx maps 4xx→healthy) and normal uvicorn startup. No 5xx, no stack traces.
2. **Remote-URL binding is correct.** `capacitor.config.ts` and the built `ios/App/App/capacitor.config.json` both set `server.url = https://leonida-preview-2.emergent.host` (overridable via `CAP_SERVER_URL`). The app correctly loads the live site, not bundled assets. Bundle ID `de.leonida.explorer` unchanged.
3. **The error is NOT the Capacitor offline fallback.** `webDir: ios-shell` / `errorPath: index.html` renders a GERMAN "Keine Verbindung" page. The user sees the ENGLISH "This page didn't load" page — that is the app's React error boundary, served from the remote site. So the WebView successfully loads the remote app; the app then throws.
4. **Supabase binding is baked into the production bundle.** `VITE_SUPABASE_URL` (`https://daxzwbkacxllrejaghym.supabase.co`) and `VITE_SUPABASE_PUBLISHABLE_KEY` are both present in the built client assets (`assets/useQuery-*.js`). `src/integrations/supabase/client.ts` throws only if these are missing — they are not.
5. **No server-function dependency.** `grep createServerFn` in `src/` = 0 matches. All data is fetched client-side via `@supabase/supabase-js` + react-query. So the missing SSR/nitro server in production does NOT break data calls.
6. **Auth storage falls back cleanly in prod.** `brokeredPreviewStorage()` only brokers over postMessage on Lovable preview zones; on the production host it returns plain `localStorage`. Not a throw source.
7. **No restrictive CSP / no stale-SW in native.** Built `_headers` only sets immutable cache on `/assets/*`. `PwaUpdatePrompt` explicitly skips service-worker registration in the native app (`isNativeApp()` guard), so no stale-SW cache in TestFlight.
8. **No route loaders / no synchronous throws in route defs.** `grep 'loader:|beforeLoad|ssr:|throw '` in `src/routes/` = 0 matches. react-query captures data errors into `.error` (no render throw). So the boundary fires from a **synchronous render throw or a code-split chunk load/parse failure** in the WebView.

## Production serving model (the key insight)
- `frontend/build.mjs` runs `vite build` with `EMERGENT_SPA=1` → produces a static SPA in `.output/public`, copied to `frontend/build`.
- `Dockerfile` copies `frontend/build` → `/usr/share/nginx/html`. `nginx.conf` serves it statically (`try_files $uri /index.html`) and proxies only `/api` → FastAPI:8001. **No Node/nitro SSR server runs in production.**
- Preview (`yarn dev` / Lovable) runs the full TanStack Start SSR server. → "works in preview, fails in production" is expected for any client-only runtime fault.
- Consequence: **there are no server-side logs for this error** (it lives entirely in the device JS runtime), which is why pod/app logs are clean despite the user-visible failure.

## Likely cause of the throw (indicated, not device-confirmed)
Because data errors are swallowed by react-query and routes have no loaders, the boundary firing across nearly all routes points to a **client-side render/module error specific to the production SPA runtime in the iOS WebView**. Strongest candidate: a **JS build-target / WebKit incompatibility** — `vite.config.ts` sets **no explicit `build.target`**, and the stack is very new (vite 8.1.5 + rolldown, React 19, `@lovable.dev/vite-tanstack-config` 2.26.5). Default targets may emit syntax newer than the TestFlight test device's iOS WebKit, causing route chunks to fail to parse/execute → error boundary on navigation. A shared synchronous render throw in the SPA bootstrap is the alternative.

NOTE: I could not reproduce the exact throw — the eph sandbox has no browser to execute client JS, there are no test credentials for the authenticated routes, and production has no SSR server to log it. The throw's LOCATION (client SPA runtime) and the preview-vs-production reason are proven; the exact throwing statement requires the device/browser console.
