# RCA — DSGVO/Security read-only diagnosis: leonida-preview-2

Scope requested: read-only diagnosis of production (https://leonida-preview-2.emergent.host).
Question: are there production / routing / secret / DB-binding faults, or only remote
Supabase RLS/migration dependencies? No data changed, no messages/accounts created or
deleted, no SQL executed. No credentials provided → live RLS tests not performed.

## Verdict
**No production / routing / secret / DB-binding error on the Emergent side.** The app is
live and correctly wired. Every DSGVO-relevant feature — community chat, private messages,
profiles, reports (melden), blocking, and account deletion — runs **client-side against the
remote Supabase (Lovable Cloud) project and is governed entirely by remote RLS policies and
RPC/migrations**. Their correctness/privacy posture is a remote dependency that cannot be
verified read-only without credentials.

## Architecture (as deployed)
- Template `farm_ts_react_mongo_base_image`, frontend_type=kubernetes, tier_0, active run
  1eca9622-7e0e-46c2-bec2-0412f1d45ffe (status success).
- Frontend: TanStack Start (Lovable) built to a **static SPA**; nginx serves
  `/usr/share/nginx/html` (`try_files $uri /index.html`) and proxies `/api` → FastAPI:8001.
  The Nitro SSR bundle (`.output/server`) is built but NOT run at runtime; it isn't needed
  because there are no server functions in use (see below).
- Backend (`backend/server.py`): minimal FastAPI, only `/api/push/*` (web-push) and
  `/api/payments/*` (Stripe → MongoDB). It is NOT the data layer for chat/DMs/profiles/etc.
- Data layer for all social/DSGVO features: `@supabase/supabase-js` called directly from the
  browser (`src/lib/db.ts` → `src/integrations/supabase/client.ts`).

## Evidence — the DSGVO features are all remote-Supabase + RLS dependent
From `src/lib/friends.ts` / components, all enforced by remote RLS/RPC:
- Block: `rpc("block_user")`, `rpc("unblock_user")`
- Report (melden): `rpc("report_user")`, `rpc("report_crew")`, `rpc("report_private_message")`
- Private messages: `from("private_messages")`, `rpc("delete_private_message")`;
  write gated client-side to `rel === "friends"` and blocked state (server RLS must enforce)
- Account deletion: `src/components/social/DeleteAccount.tsx` → `sb.rpc("delete_my_account")`
  (storage cleanup of buckets `avatars`, `spot-photos` best-effort after)
- Admin moderation: `admin_list_reports`, `admin_update_report` (behind has_role admin)
- Notifications: `from("notifications")`

Migration / RLS source of truth is **remote, not in an auto-applied pipeline path**:
- `supabase/` contains only `config.toml` — **no `supabase/migrations/` directory**.
- The schema + RLS + RPCs live as manual SQL in `docs/migrations/*.sql`
  (001_leonida_schema, 002_auth_roles/has_role, 004_profile_badges, 004b_profile_privacy_lock,
  011_ios_app_push_konto_loeschen = `delete_my_account`, 019_coin_balance, etc.) — applied by
  hand to the Lovable Cloud project.
- The app self-detects un-applied migrations at runtime: `src/lib/db.ts isMissing()` treats
  PostgREST codes PGRST202/PGRST205/42883/42P01/42703/PGRST200 ("function/table/column does
  not exist") as "compatibility mode". DeleteAccount explicitly shows
  "Konto löschen wird nach dem Datenbank-Update (SQL 011) aktiv." if `delete_my_account` is
  absent. => A feature appearing "broken" here = a missing remote migration, NOT a prod fault.

## What could NOT be verified (needs credentials / live tests)
Whether the remote Supabase project actually has (a) all migrations applied and (b) correct,
enabled RLS policies on `private_messages`, `notifications`, `profiles`, blocks, reports —
i.e. that the anon/publishable key cannot read/write across users. This is the core DSGVO
question and it is purely a remote Supabase configuration matter; read-only diagnosis without
credentials cannot confirm it (as the requester noted).
